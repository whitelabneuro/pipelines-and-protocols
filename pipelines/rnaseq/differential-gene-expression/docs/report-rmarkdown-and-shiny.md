# Report, R Markdown, and Shiny outputs

This document explains how White Lab downstream bulk RNA-seq differential gene expression projects should use the reporting and interactive output layers produced by `nf-core/differentialabundance`.

For many studies, the downstream pipeline does not only generate statistical tables. It also produces human-readable and interactive outputs that are extremely useful for rapid review, communication, teaching, and further customisation.

In White Lab practice, these reporting layers are important because they help bridge the gap between:

- raw pipeline outputs
- first-pass interpretation
- internal lab discussion
- collaborator sharing
- custom follow-up reporting

This page focuses on three major output types:

- the HTML report
- the R Markdown report bundle
- the Shiny app output

---

## Why these outputs matter

A downstream DGE run may produce many tables and figures, but users often need a more integrated way to review and communicate the analysis.

The reporting and interactive outputs are valuable because they can:

- provide a quick overview of the run
- reduce the need to open many raw result files manually
- support accessible discussion of results
- serve as the basis for customised reports or presentations
- allow more flexible exploration of the outputs

In White Lab practice, these layers are often among the first things reviewed after the core run completes.

---

## Core principle

These outputs are best understood as **interfaces to the analysis**, not replacements for the underlying result tables.

That means:

- the HTML report is a useful integrated summary
- the R Markdown bundle is a useful reporting resource
- the Shiny app is a useful exploration layer

but none of these should be treated as a substitute for preserving and understanding the core differential result tables and the run provenance.

---

## The three reporting layers

### 1. HTML report
A human-readable summary output generated by the pipeline.

### 2. R Markdown reporting bundle
A reusable report source package that can be modified and re-rendered later.

### 3. Shiny app output
An interactive application generated by the pipeline for browsing and exploring results.

These layers serve different but complementary purposes.

---

## HTML report

The HTML report is usually the most convenient first entry point into a completed downstream run.

It brings together key information from the analysis into a single readable output and is often the quickest way to get a high-level sense of:

- what was run
- which contrasts were performed
- what the major results look like
- what exploratory and differential plots were generated
- whether the outputs look broadly sensible

### White Lab view of the HTML report

The HTML report is especially useful for:

- first-pass run review
- quick lab discussion
- collaborator sharing
- checking that a run has produced the expected types of output
- revisiting a study without manually opening many separate files

For many users, this should be the first output opened after a successful run.

That is good practice, but it should then be followed by direct inspection of the main differential result tables.

---

## What the HTML report is good for

The HTML report is particularly useful for:

- obtaining a rapid integrated overview
- reviewing plots and summaries in context
- checking whether contrasts and outputs appear reasonable
- summarising the analysis in a more human-friendly way than raw result directories
- providing a lightweight study summary to others

It is often the fastest way to answer the question:

**Did this run produce something that looks coherent and worth deeper review?**

---

## What the HTML report is not for

The HTML report should not be treated as:

- the sole retained analytical output
- a substitute for the result tables
- the only place from which conclusions are drawn
- a replacement for documenting matrix, metadata, contrasts, and provenance choices

It is a highly useful summary layer, but serious downstream interpretation still depends on the underlying tables and design context.

---

## R Markdown reporting bundle

The pipeline also produces report materials that support later reuse and customisation through R Markdown.

In White Lab practice, this is particularly valuable because it allows the standard pipeline reporting layer to become the starting point for a more tailored study-specific report if needed.

### White Lab view of the R Markdown bundle

This output is useful for:

- understanding how the standard report was generated
- editing the report structure or narrative later
- re-rendering a report after small modifications
- adapting the report for internal lab meetings, collaborator updates, or teaching
- building a bridge between standard nf-core outputs and more bespoke downstream summaries

It is one of the most flexible reporting assets produced by the workflow.

---

## When the R Markdown bundle is especially useful

The R Markdown bundle is particularly useful when:

- the default HTML report is good, but needs light modification
- a study needs a more tailored narrative
- selected figures or sections need to be adjusted
- the same reporting adjustments are likely to be repeated across studies
- a more presentation-ready or teaching-friendly summary is needed

It is also useful for users who want to understand the report-generation logic rather than only consume the final static output.

---

## White Lab recommended use of the R Markdown bundle

A good White Lab workflow is usually:

1. review the default HTML report first
2. decide whether the standard report is sufficient
3. if not, use the R Markdown bundle as the starting point for controlled modifications
4. save any study-specific custom reporting outputs clearly alongside the study record

This avoids unnecessary duplication of effort while preserving the advantages of the pipeline-native reporting layer.

---

## Important distinction: pipeline report versus custom report

White Lab users should distinguish clearly between:

### Pipeline-native reporting
This is the reporting layer generated directly by `nf-core/differentialabundance`.

### Custom downstream reporting
This refers to additional report work created later by White Lab users, for example:
- custom R Markdown summaries
- presentation-oriented figure decks
- lab meeting summaries
- manuscript-supporting result summaries

The pipeline-native report is usually the first reporting pass.

Custom reporting should be built on top of it deliberately, not confused with it.

---

## Shiny app output

If Shiny app generation is enabled, the pipeline can produce an interactive ShinyNGS-based application.

This can be one of the most powerful outputs for exploratory review and data browsing.

### White Lab view of the Shiny app

The Shiny app is especially useful for:

- exploring contrasts interactively
- browsing result tables more flexibly
- reviewing plots and results without opening multiple raw files
- supporting meetings and discussion
- helping collaborators engage with the results
- making a completed study more accessible to less computationally focused users

In many White Lab studies, this should be seen as a highly valuable optional output rather than a niche extra.

---

## What the Shiny app is good for

The Shiny output is particularly useful for:

- interactive exploration after the run completes
- comparing contrasts dynamically
- helping users inspect results in a more fluid way than static files allow
- supporting study review by multiple users
- allowing a project to be revisited later in an accessible form

This is especially useful in projects with:
- multiple contrasts
- large result sets
- many exploratory or differential visual outputs
- a need for collaborative review

---

## What the Shiny app is not for

The Shiny app should not be treated as:

- the sole retained output of the study
- a substitute for result table retention
- a replacement for provenance documentation
- a guarantee that the analysis itself has been interpreted correctly

It is an interface layer and exploration tool, not the entire study record.

---

## White Lab default attitude toward Shiny generation

In general, White Lab should regard Shiny app generation as:

- useful
- encouraged for many standard runs
- especially valuable for exploration and handover
- worth retaining where practical

Automatic external deployment should usually not be the default.

For most studies, it is preferable to generate and retain the app locally within the output structure unless there is a specific reason to deploy it elsewhere.

---

## Local use of the Shiny app

In White Lab practice, the most common use case will usually be local or internal use of the generated app.

This is appropriate for:

- study review
- local exploration
- internal collaborator discussion
- checking results interactively before making more formal summaries

This mode is often sufficient and avoids adding unnecessary deployment complexity to standard studies.

---

## External deployment considerations

Some studies may eventually benefit from hosting or broader sharing of a Shiny app.

If that is ever done, the study should record clearly:

- whether deployment occurred
- where it was hosted
- which exact run output the app corresponds to
- whether the deployed version is still current

However, this should be treated as an optional extension, not the default expectation.

---

## How to decide whether the reporting outputs are sufficient

After a run completes, a White Lab user should ask:

### Is the HTML report enough?
If the HTML report already communicates the main findings clearly, further custom reporting may not be necessary immediately.

### Is interactive exploration helpful?
If the study has many contrasts or requires discussion with others, the Shiny app may be especially useful.

### Is a more tailored narrative needed?
If the standard report needs adaptation for grant writing, presentation, teaching, or manuscript planning, the R Markdown bundle may become the most valuable reporting asset.

The answer will vary by study, but the key is to use these outputs intentionally.

---

## Suggested White Lab review order for reporting outputs

A sensible order is:

### 1. Open the HTML report
Use it as the first integrated summary of the run.

### 2. Check whether the Shiny app was generated
If yes, review whether it provides useful additional exploration value.

### 3. Decide whether the standard report is sufficient
If the standard report is enough, document and retain it.

### 4. If needed, inspect the R Markdown bundle
Use it as the basis for controlled report customisation.

This sequence keeps reporting work efficient and avoids unnecessary duplication.

## White Lab communication use cases

These reporting outputs are particularly valuable in different communication contexts.

### Internal lab review
Most useful:
- HTML report
- Shiny app
- selected result tables

### Collaborator update
Most useful:
- HTML report
- selected static plots
- selected tables
- Shiny app where interactive review is helpful

### Grant or presentation preparation
Most useful:
- R Markdown bundle
- selected report plots
- pathway outputs
- custom follow-up reporting

### Teaching and onboarding
Most useful:
- HTML report
- Shiny app
- worked example outputs

This is one reason these outputs deserve dedicated documentation.

---

## Common mistakes to avoid

### Treating the HTML report as a substitute for result tables
It is a summary interface, not the sole analytical output.

### Ignoring the R Markdown bundle
This can be one of the most useful assets when a more tailored report is needed.

### Generating the Shiny app but never using it
If it is enabled, it should be reviewed as a potential exploration and handover tool.

### Letting custom reporting drift away from the pipeline provenance
Any custom report should still remain clearly linked to the run and its core result files.

### Confusing interface quality with analytical quality
A polished report does not by itself mean the underlying analysis is sound.

---

## Relationship to resumed runs

Reporting outputs should also be interpreted in the context of run identity.

When a study includes resumed runs, users should be able to tell:

- which HTML report belongs to which run
- whether the Shiny app reflects the initial run or an extended pathway run
- whether a custom report was based on the initial DGE run or a later analytical branch

This is another reason why each meaningful run should preserve a clear identity and output directory.

---

## What should usually be retained

In most White Lab studies, the following reporting-related outputs are strong candidates for retention review:

- the main HTML report
- the R Markdown reporting bundle
- the Shiny app output where generated and useful
- any clearly defined custom reports derived from these
- enough provenance to link them back to the exact run

The exact retention policy is described more fully in `retention-and-handover.md`.

---

## Relationship to interpretation

These outputs are most useful when they sit within a good interpretation workflow.

A reporting output should always be read in the context of:

- the matrix choice
- the metadata and contrasts
- the quality of the sample-level behaviour
- the main differential result tables
- the pathway analysis settings if applicable
- the run identity and provenance

The report is the interface to the analysis, not the entire analysis.

---

## Summary

`nf-core/differentialabundance` can provide three especially valuable reporting layers for White Lab downstream DGE studies:

- the HTML report for integrated first-pass review
- the R Markdown bundle for controlled report customisation
- the Shiny app for interactive exploration and handover

In White Lab practice, these outputs should be treated as important communication and exploration tools, but always as companions to, not replacements for, the underlying differential result tables and study provenance.
